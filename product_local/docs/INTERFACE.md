# Interfaz operacional R2 0.1.0

Autoridad de integración acordada A/B el 2026-10-03. Autor: `/root/r2_b_supervisor`. Implementa una variante local estricta de los contratos R1 recibidos. No modifica Input/Result FP1, ni admite semántica física. `OPERATIONAL_PROFILE.md` fija operación y fallos. Una variante no descrita se rechaza; no se interpreta favorablemente por omisión.

## Funciones Python

`policy.loads_strict(raw: bytes) -> dict`: JSON UTF-8; rechaza claves duplicadas, floats, NaN/Infinity. Enteros JSON se reservan a contadores operacionales; magnitudes matemáticas son cadenas exactas.

`policy.canonical_bytes(obj) -> bytes`; `policy.query_digest(query) -> str`: JSON ordenado, separadores compactos, UTF-8 sin escapes ASCII añadidos. El digest de query se calcula, nunca se recibe como prueba.

`policy.validate_request(request, blob_reader) -> dict`: verifica estructura, referencias, DAG y bytes; devuelve la solicitud validada, sin conclusiones añadidas. `blob_reader(artifact_id) -> bytes`. No abre URLs ni busca rutas fuera del registro del controlador.

`policy.assess_source(assessment, artifacts) -> dict`: `artifacts` es mapping `id -> {metadata, bytes}`. Recalcula ejes/veredicto y conserva evidencia; no recibe el veredicto del llamador como autoridad.

`operations.execute_operation(operation, context) -> outcome`. Context incluye `request`, `query`, `blob_reader`, `artifacts`, `baseline_r0`, `baseline_r1`, `budget`, `cancel_check`. Cancelación/agotamiento se registran aparte del Result FP1.

`policy.build_response(request, operation_results, context) -> dict`: context contiene `execution` (estado PE, causa/progreso), `ledger` (obligaciones/historial de trabajo ya conservados), `artifacts` (registro de recibidos/esperados), `request_ref` (revisión/digest real), `versions`, `budget_used` y `closure_reason` cuando proceda. Sólo outcomes internos ligados a query/operación existentes alimentan conclusiones.

`controller.execute(request_path, case_dir, baseline_r0, baseline_r1, cancel_file=None) -> dict`. El controlador gestiona commit/reanudación y artefactos; no delega la confianza en los bytes a expected/status enviados por un cliente.

## Solicitud y consultas

Root cerrado: `format:"genius-local-request/0.1.0"`, `request_id` string no vacía, `revision` entero >=1, `supersedes` null inicial o referencia explícita de revisión/digest, `queries`, `artifacts`, `obligations`, `budget`, `operations`, `novelty`.

Continuación: `supersedes:{revision:<última revisión del Store>,sha256:<HEAD>}`; `request.revision` lógica aumenta en uno. Store y solicitud tienen revisiones distintas (un intento puede producir varios commits). Importación: máximo 256 artefactos y 32 MiB agregados por solicitud, además de 8 MiB por artefacto y 4 MiB de solicitud. Son límites previos al trabajo y no magnitudes matemáticas.

Límites internos recibidos antes de congelar: outcomes agregados 8 MiB, respuesta lógica 32 MiB y snapshot lógico 64 MiB. El Store puede dividir un objeto lógico en chunks CAS de hasta 8 MiB: no aumenta el límite de un artefacto recibido individual. Un exceso se informa como agotamiento/error acotado, sin decisión falsa. Worker FDQ: timeout externo <=60 s, memoria RLIMIT_AS 1 GiB cuando Linux lo permite, recepción stdout+stderr <=2 MiB; conservar prefijo/truncated y no parsear como respuesta completa. El proceso se observa por polling; el límite de recepción no es promesa de tamaño de disco instantáneo estricto.

La serialización persistida usa `storage_format:"genius-local-snapshot-refs/0.1.0"`, referencia al request original y manifests `outcome_refs`, `ledger_ref`, `response_ref` cuando existe respuesta publicada. Cada manifest `{sha256,size,chunks:[CAS_ref]}` conserva digest/tamaño del objeto lógico completo y orden de chunks; cada CAS_ref identifica bytes recibidos por digest/tamaño/ruta. El lector reconstruye y verifica antes de usar. El snapshot externo no implica que exista un objeto monolítico mayor de 8 MiB.

Un exceso de respuesta/snapshot compromete un estado BUDGET_CLOSED con PE_BUDGET_EXHAUSTED y conserva `unpublished_response_ref` cuando existe candidata no publicada. La CLI devuelve stderr y código2, formato `genius-local-cli-error/0.1.0`, con PT_FAILED, causa operacional, referencia HEAD y decisión NOT_PUBLISHED: no es un sobre RC truncado ni una decisión matemática. `inspect` permite reconocer ese estado; `recover` no lo convierte a PE_UNKNOWN ni publica automáticamente una respuesta demasiado grande. Una solicitud posterior pertinente puede continuar mediante nueva revisión.

`budget`: `{max_operations: int, max_certificates: int, certificate_timeout_seconds: int}` con 0..64, 0..2 y 1..60 respectivamente; límites de tamaño/consultas del perfil no aumentan mediante estos campos. `novelty`: `{reason: string, changed_refs: [string]}`; el controlador comprueba un delta pertinente contra la revisión previa, sin confiar en la prosa ni en IDs nuevos. Inicial usa reason explícito y lista vacía.

`artifacts`: lista de `{id, role, path, sha256, evidence_kind, permissions}`. `role`, `path`, `sha256` son strings; digest SHA-256 real de los bytes conservados. `evidence_kind` es PRIMARY_OBSERVATION, PRIMARY_DOCUMENT, RECEIVED_DERIVATION, SYNTHETIC_STIPULATION, NORMATIVE_DECLARATION o SECONDARY_CONTEXT. `permissions` registra `{access: "ALLOWED"|"UNKNOWN"|"DENIED", use: "ALLOWED"|"UNKNOWN"|"DENIED", basis: string}`. Las declaraciones de permiso no se autentican automáticamente; UNKNOWN/DENIED impiden reutilizar como fuente admitida. Un digest identifica bytes, no verdad ni permiso externo.

`queries`: lista de `{id, revision, kind, target_spec, scope, norm, artifact_refs, obligation_refs}`. `kind` es `component`, `frontier` o `selector`. `target_spec` tiene exactamente cinco ejes: `identity`, `unit`, `period`, `population`, `method`; cada valor es un descriptor no vacío o celda producto desconocida explícita. Consumo de una fuente requiere descriptores definidos. `scope` es el objeto cerrado por operación descrito abajo. `norm` es regla versionada/objeto FP1 recibido o celda PV_UNKNOWN/PV_NOT_APPLICABLE explicada; no se infiere por orden de IDs. El digest cubre **todo** query, incluidas referencias, regla y alcance.

Cada `obligation` conserva todos los campos IC01: `id`, `revision`, `query_ref`, `affected_claims`, `primary_cause`, `secondary_causes`, `classification_basis`, `provenance`, `input_spec`, `derivation_rule`, `dependencies`, `owner`, `permitted_use`, `prohibited_inferences`, `status`, `closure`, `reopen`, `next_action`, `budget_ref`, `attempts`. Se admiten las nueve causas IC02 exactas, sin duplicar primaria/secundarias. Dependencies lista `{ref,revision,role}` forma DAG entre obligaciones del expediente; role es input/rule/interface/permission/guarantee. `owner:{role,task,assigned_person}` permite assigned_person `"UNKNOWN"`; no atribuye aceptación humana. `closure:{predicate,witness_refs,verifier,verified}` entra sólo con verified:false y estado OPEN/READY/BLOCKED/DEFERRED/CANCELLED; no se admiten cierres del cliente. El ejecutor añade testigo y verified:true cuando la operación recibida permite ese cierre. `reopen:{condition,affected_refs}`. `input_spec` conserva objeto/campo/tipo/unit/period/population/method/state/reason; estado KNOWN/UNKNOWN/NOT_APPLICABLE/OUTSIDE_PROFILE. `derivation_rule` registra kind RULE/PENDING_RULE/NO_DERIVATION y razón/regla/dominio según aplique. `classification_basis`, `provenance`, `permitted_use`, `prohibited_inferences`, `attempts` conservan evidencia y motivos explícitos; no se infiere semántica de una etiqueta B01.

## Operaciones y binding

Cada operación: `{id,query_ref,kind,obligation_refs,parameters}`. Sus referencias deben resolver en la misma solicitud. Orden de fases fijo: REUSE, DERIVE_HOURS, CERTIFY_FDQ/PROVE_IRRELEVANCE, EXPAND_MODEL, ASSESS_SOURCE, REQUEST_INPUT. Los pasos ausentes se registran NOT_APPLICABLE con causa; omitir ejecución no aporta evidencia de cierre.

La variante exige al menos una obligación resoluble por consulta y por operación, para que una salida PV_UNKNOWN siempre pueda identificar su pendiente sin crear una obligación ficticia. El único predicado de cierre automático es `EXACT_QUERY_RESULT_RECEIVED`, con affected_claims exactamente `[query.id]`, causa admitida por la operación y dependencias ya cerradas en alcance. Otro texto de predicado se conserva como pendiente: un resultado formal puede responder la query sin verificar ese predicado arbitrario. La regla se aplica antes de persistir el efecto de cierre, además de comprobarse al construir la respuesta. REQUEST_INPUT de una obligación ya cerrada se registra NOT_APPLICABLE; no se genera una pregunta innecesaria.

Antes de recalcular, el controlador busca resultados VERIFIED/CONDITIONAL en el historial verificado del mismo expediente. Clave conservadora: query íntegra, kind/regla/parameters, referencias/digests de artefactos y dependencias; cambio de cualquiera invalida reutilización. Un recibo coincidente se reutiliza con referencia a su revisión original y sin declarar nueva ejecución. Si no coincide, el worklog identifica el inventario local examinado y su alcance, sin afirmar ausencia global. Esta búsqueda no convierte REUSE/1 en otra regla: reusa el resultado de la operación original bajo su mismo binding. El intento nuevo aún requiere novedad pertinente (por ejemplo otra consulta añadida); un intento idéntico no se habilita por existir un recibo.

|---|---|---|
| REUSE `{artifact_ref,pointer,assessment}` | component; scope `{operator:"REUSE/1",artifact_ref,pointer}`; JSON pointer real en bytes y assessment ligado al query/claim. Los cinco ejes deben resolver y el uso debe estar permitido | Valor/celda documental; sintético es CONDITIONAL. No es selección ni nueva observación |
| DERIVE_HOURS `{artifact_ref,rule_id:"CONTRACT_HOURS/1",assessment}` | component; scope `{operator:"CONTRACT_HOURS/1",purpose:"FORMAL_CONDITIONAL"}`; artefacto JSON `{assignments:[{id,credit_hours:cell}],target_hours:cell}`. IDs únicos; PV_KNOWN racional canónico y unit `h_contractual`; PV_UNKNOWN se propaga | sum,excess,deficit exactos; desconocido conserva razones y obligaciones. No duración física, descanso, consentimiento ni utilidad |
| CERTIFY_FDQ `{input_ref,result_ref,certificate_ref}` | frontier o selector; scope descrito debajo y norm igual Input.selection; bytes Input/Result intactos; certificado recibido ejecutado en subproceso acotado | Sólo DS-R1/FDQ_FINITE_PATCH recibido, siempre uso formal condicional; ninguna pertenencia real a Γ inferida |

Otro propósito/query se rechaza |
| EXPAND_MODEL `{reason,affected_dependencies}` | Consulta con obligación de modelo/capacidad; conservar todas las dependencias. No se materializa un modelo admitido | UNRESOLVED con trabajo concreto y dueño; nunca cierre por ampliar prosa |

| REQUEST_INPUT `{obligation_ref,prompt,unknown_allowed:true}` | Obligación externa/preferencia/modelo/capacidad pertinente y responsable funcional; pregunta local no enviada | UNRESOLVED; no contactar personas ni certificar adquisición |

Precisiones de conformidad de Ronda1, sin ampliar reglas: DERIVE_HOURS exige `query.target_spec.unit == "h_contractual"` además de los ejes compatibles y las celdas contractuales de entrada; un descriptor físico u otra unidad se rechaza. REUSE admite una celda producto directa válida o un literal sin celdas producto descendientes. Un árbol literal que contenga cualquier celda PV anidada, o una celda PV_KNOWN cuyo value contenga otras celdas PV, queda OUTSIDE_PROFILE con `REUSE_NESTED_PRODUCT_STATE_OUTSIDE_PROFILE`: no se envuelve como conocido ni se cierra su obligación. Los bytes permanecen conservados y la celda PV_UNKNOWN directa sigue desconocida. Una celda conocida directa debe coincidir en unidad con la fuente admitida antes de cualquier puente permitido.

FDQ scope exacto: `{profile:"FDQ_FINITE_PATCH/0.1.0",input_sha256,original_result_sha256,domain_sha256,target,horizon:"1",scenarios,query_flags,real_domain_membership:"NOT_ESTABLISHED"}`. `domain_sha256` se calcula sobre certificate.domain canónico. target coincide con Π completa y certificate.target; scenarios con IDs del Input; query_flags coinciden con certificate.query y con kind (frontier-only o selector-only). El cliente puede crear dos consultas separadas para ambas. No se admite certificar una query y publicar otra. `norm` coincide con Input.selection. Support/boundary/model y todas las dependencias quedan ligados por digest íntegro del Input, no extraídos selectivamente.

FDQ target_spec también se deriva de los bytes, sin etiquetas empíricas libres: `identity="FP1_INPUT_SHA256:"+sha256(input_raw)`, `unit="policy_id_set"` para frontier o `"policy_id"` para selector, `period="H="+input.meta.horizon`, `population="DECLARED_PI:"+JSON_canónico(sorted(policy.id))`, `method="FDQ_FINITE_PATCH/0.1.0"`. Un target distinto se rechaza FDQ_TARGET_SPEC_BINDING. El propósito es impedir que una garantía formal sobre un Input aparezca vinculada a otra población o método por etiquetas del llamador.

Outcome interno: `{operation_id,query_ref,query_sha256,kind,status,reason,claim_source,value,evidence,obligation_effects,artifact_refs}` y opcional `execution_state`. Status VERIFIED/CONDITIONAL/UNRESOLVED/OUTSIDE_PROFILE/REJECTED/ERROR/INCONCLUSIVE. `evidence` y `obligation_effects` son listas; ningún efecto cierra una obligación de otra consulta o de hecho/modelo externo por un certificado formal. value es celda producto u objeto de celdas exactas. Un certificado SUFFICIENT es CONDITIONAL; NOT_ACCEPTED es REJECTED, no refutación de la tarea; OUTSIDE_PROFILE se conserva; INCONCLUSIVE no es inviabilidad.

## Fuentes y exactitud

Assessment conserva campos SC01: `assessment_id`, `revision`, `query_ref`, `claim`, `intended_use`, `target_spec`, `source_ref`, `source_locator`, `source_version`, `source_digest`, `observed_or_received_at`, `relevant_period`, `access_and_permissions`, `evidence_kind`, `transformation_chain`, `axes`, `conflicts`, `verdict`, `owner`, `closure`, `reopen`. `verdict` de entrada es `PENDING`; la salida lo calcula. `axes` mapping cinco nombres, cada `{status,source_value,target_value,basis,affected_claims}` y `bridge_ref` sólo en BRIDGED. status de entrada no sustituye comprobación de igualdad. Basis referencia bytes/localizador inspeccionable; ausencia de soporte=>UNKNOWN. Source_digest/source_ref y target_spec deben corresponder a bytes y query; evidence_kind corresponde al artefacto.

Único puente automático: `EXACT_UNIT_SCALE/1`, escala racional positiva canónica y mismo constructo explícito, con testigo en transformation_chain y artefacto. No convierte proxies ni poblaciones. Otros puentes/admisiones/conflictos resueltos manualmente quedan fuera del subperfil. Un conflicto no resuelto conserva todas las fuentes y produce SC_UNRESOLVED; no se elige fuente por recencia/prestigio/favorabilidad. Sintético compatible=>SC_CONDITIONAL_MODEL_ONLY, nunca observación.

Precisión operacional de fuentes: `basis:{artifact_ref,pointer}` apunta a un objeto recuperable; source_value debe igualar ese objeto y target_value a query.target_spec[axis]. En eje unidad se admiten descriptores `{construct,unit}`. Puente: entrada transformation_chain `{id,rule_id:"EXACT_UNIT_SCALE/1",source_unit,target_unit,factor,construct,basis}`; bridge_ref apunta a id. La tabla admitida es min→h=1/60, h→min=60/1, g→kg=1/1000, kg→g=1000/1, con constructo de duración física o masa respectivamente. No convierte minutos físicos a crédito contractual. El factor declarado se coteja con esa tabla, no se acepta un número arbitrario. La base documental del puente se conserva; su autenticidad sigue sin ser validada automáticamente. Conflicto operacional `{source_refs,condition,scope,consequences,owner,resolution:"UNRESOLVED",rule}` conserva las fuentes nombradas.

Precisión de obligaciones: input_spec usa exactamente object/field/type/unit/period/population/method/state/reason. `derivation_rule` RULE contiene kind/id/version/procedure/domain/basis; PENDING_RULE y NO_DERIVATION contienen kind/reason. PENDING_RULE admite además obligation_ref opcional, que debe resolver y aparecer como dependencia con role=rule si existe: no puede ocultar una autorreferencia fuera del DAG. Una basis tipada `{artifact_ref,pointer}` de RULE debe resolver sus bytes/localizador, y se normaliza por su contenido al comparar aliases; una declaración documental de regla no admite su semántica por sí sola. Reglas futuras, testigos o clasificaciones desconocidas no habilitan cierres por declarar campos completos.

Una base aún no adquirida se expresa `{state:"NOT_ACQUIRED",reason}` y produce eje UNKNOWN; no una referencia inventada. Un puente o resolución manual fuera de la variante produce SC_UNRESOLVED con `profile_limitations` explícitas (SC no define un enum OUTSIDE_PROFILE); la operación puede comunicar OUTSIDE_PROFILE sin promover compatibilidad. NOT_APPLICABLE no se admite por etiqueta sin prueba incorporada en la regla soportada.

La admisión recorre todas las premisas consumidas: fuente principal, bases de ejes y bases de puentes. `premise_artifact_refs`, `conditional_premise_refs` y `blocked_premise_refs` hacen visible esa cadena. Si cualquier premisa es SYNTHETIC_STIPULATION, el resultado compatible sólo es SC_CONDITIONAL_MODEL_ONLY; si algún permiso consumido es UNKNOWN/DENIED, SC_ACCESS_BLOCKED. No se oculta una premisa sintética detrás de una fuente principal etiquetada PRIMARY_DOCUMENT.

Un conflicto también puede aparecer **entre dos resultados de operaciones** aunque cada fuente haya sido admitida por separado. Se comparan valores/unidades de la misma consulta, sin convertir una diferencia de procedencia en diferencia matemática; las componentes conocidas de una respuesta parcial también pueden contradecir otra. Antes de aplicar cierres, la obligación de la consulta conflictiva y sus descendientes en el DAG quedan o se reabren BLOCKED, con verified:false, referencias a recibos, responsable conservado y acción de resolver el conflicto bajo regla admitida. Ningún efecto posterior vuelve a cerrarlas mientras persista ese conflicto. El mismo estado se persiste en cada checkpoint y se usa al decidir si omitir REQUEST_INPUT. Se retienen todos los recibos, las revisiones previamente comprometidas y las subrespuestas; no se promedian ni elige un valor favorable. Un descendiente con recibo propio puede conservarlo como parcial, pero requiere revalidación de sus dependencias.

Celda producto variante exclusiva RC03: PV_KNOWN `{state,value,unit,basis}`; PV_UNKNOWN `{state,reasons,obligation_refs}`; PV_NOT_APPLICABLE `{state,reasons,scope}`; PV_OUTSIDE_PROFILE `{state,reasons,profile_ref}`. Sólo PV_KNOWN tiene value. Q nuevo canónico n/d (denominador>0, irreducible); cero=0/1. No floats, null matemático, cero por ausencia, medias de fuentes conflictivas ni probabilidad por ignorancia.

Enteros JSON tampoco representan magnitudes matemáticas en PV_KNOWN, incluidos valores anidados: usar cadenas exactas Nat/Q/Bit. Un booleano de verdad puede ser un valor nominal probado; no se confunde con el entero 0/1 ni se convierte al Bit FP1. Los enteros operacionales de revisión/presupuesto permanecen enteros JSON fuera de celdas matemáticas.

## Respuesta y cierre

Sobre completo RC01 con cuatro capas ortogonales, artefactos originales/esperados y calidad RC06 sin score global. VERIFIED/CONDITIONAL aplicable puede justificar sólo la consulta formal/componente correspondiente; unknown, fallo o presupuesto no justifican selección/inviabilidad. Frontera y selector se responden separadamente. Campo no consumido o contrato/perfil desconocido produce dependencia/fuera de perfil explícito. Utilidad, comprensión, adopción y fidelidad empírica siguen NOT_ASSESSED.

PR_PROVEN_INFEASIBLE sólo se expone si una garantía recibida y ejecutada aporta refutación persistente de **toda Π**; frontier vacía, valores desconocidos o error no bastan. Si esa prueba no está expuesta por la primera capa, la solicitud de ese estado queda OUTSIDE_PROFILE con límite expreso. Un positivo de conjunto puede cerrar una consulta frontier sin seleccionar; una consulta selector con preferencia sin definir queda dependiente.

Una consulta formal FDQ sobre el **estado del selector** puede tener respuesta justificada `OUTSIDE_DOMAIN` con causa `SELECTION_DISABLED`, `SELECTION_EMPTY` o `SELECTION_NOT_UNIQUE` acreditada en todas las completaciones. Eso es PR_JUSTIFIED_RESULT del objeto exacto/causa, sin política seleccionada; no es PR_SET_OR_INCOMPARABLE si no se pidió y probó la frontera. Una solicitud práctica de elegir sin norma admitida sigue dependiente. No inferir un conjunto o selección desde el nombre del estado.

Ledger integra obligations/worklog/attempts, preserva clasificación/procedencia, registra fase APPLIED/NOT_APPLICABLE/BLOCKED y marca cualquier deducción externa con claim_source. Cierre local conserva respuestas verificadas y pendientes. Continuación exige delta pertinente y nueva revisión enlazada; modificar sólo IDs/prosa de novelty no admite reintento. Cancelación externa sin recibo no declara PE_CANCELLED del subcálculo; presupuesto no prueba imposibilidad. Estas reglas se prueban en fixtures identificados y no constituyen un estudio B01 ni una admisión de macetas.

Excepción operacional explícita a delta matemático: una interrupción comprobada con trabajo PE_UNKNOWN, identificada por estado/revisión real del Store, permite solicitar reinicio en revisión nueva aunque los datos sean idénticos. La novedad es el estado operacional recibido, no la palabra «reiniciar» en novelty. Se conservan resultados previos y presupuesto declarado; no se promete reanudar internamente el Kernel. Un expediente COMPLETE no se reintenta sin delta pertinente. Dos intentos sin avance siguen activando revisión del encargo; no se reinicia automáticamente el contador.

Solicitud de ese reinicio: `novelty.reason="RETRY_INTERRUPTED_OPERATION"` y changed_refs incluye un operation.id efectivamente iniciado sin recibo en la revisión que se supersede. El Store comprueba ese hecho; el literal por sí solo no concede novedad.

La comparación de novedad resuelve aliases sólo en posiciones tipadas de referencia (query/obligación/operación/artefacto/evaluación/puente). Renombrar coherentemente esas identidades conserva significado y no habilita cómputo ni reinicia progreso. Los descriptores y valores literales no se reemplazan mediante una sustitución global de strings: un valor que coincida accidentalmente con un ID sigue siendo un valor.

En la fuente tipada CONTRACT_HOURS/1 también se resuelven los obligation_refs de una celda PV_UNKNOWN hacia las obligaciones registradas; renombrarlos coherentemente no aporta un crédito nuevo. Assignment.id y los valores literales se conservan. Consultas u operaciones semánticamente duplicadas se comparan como un conjunto para esta comprobación; multiplicar aliases no genera novedad. Esta normalización sólo controla la autorización de un nuevo intento: el almacenamiento original y la caché siguen ligados a bytes/digests exactos.

Procedencia del productor: cada snapshot nuevo conserva `producer:{format:"genius-local-producer/0.1.0",modules,sha256}`, calculado por el ejecutor sobre los siete módulos runtime `__init__`, `__main__`, controller, store, policy, operations y fdq_worker. La reutilización exige igualdad de esa identidad y la clave completa anterior. Recibos de C1 sin marca o producidos por código distinto se conservan históricamente pero no evitan las guardas actuales. La reevaluación explícita usa reason `REVERIFY_IMPLEMENTATION_CHANGED`, changed_refs con operation.id y revisión supersedes válida; sólo se admite si falta la marca previa o cambió realmente el hash del productor. Ese texto sin cambio comprobado no permite repetir. No es autenticación contra un administrador malicioso ni aceptación automática de una implementación nueva.

Una continuación ordinaria bajo productor cambiado/ausente se rechaza `IMPLEMENTATION_CHANGED_REQUIRES_EXPLICIT_REVERIFICATION` antes de reinterpretar una gramática histórica más débil; no basta aportar un nuevo texto o cambiar datos para omitir la identificación explícita del nuevo intento. Normalizar una fuente CONTRACT_HOURS/1 para novedad requiere primero validar la gramática de sus celdas y su vínculo a obligaciones de la misma consulta. Reevaluar permite ejecutar las guardas actuales, nunca declara correcta una conclusión histórica por adelantado.

La misma guarda se aplica a recover sobre un snapshot RUNNING con productor cambiado/ausente: rechaza con ese motivo y no cambia HEAD ni fabrica un sobre nuevo a partir de recibos antiguos. Únicamente una continuación explícita REVERIFY_IMPLEMENTATION_CHANGED, enlazada a ese RUNNING real y a una operación, permite un intento nuevo vacío de outcomes antiguos, bajo el bloqueo de escritor y las guardas actuales. Las revisiones y huérfanos anteriores se conservan. CLOSED/RECOVERED_CLOSED puede devolver la respuesta histórica ya almacenada; leerla no es recertificarla bajo otro productor.

El worker importa las fuentes recibidas fijadas por digest desde una copia temporal que contiene sólo esos módulos, sin añadir los directorios originales de R1/R0 a sys.path. Los hermanos adicionales no fijados no se ejecutan por vecindad. La biblioteca estándar y el entorno Python siguen siendo dependencias del runtime; esto no promete un sandbox general de ejecución.
